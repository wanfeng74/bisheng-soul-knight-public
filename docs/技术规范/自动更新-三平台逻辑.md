# 自动更新逻辑 —— rk / cvis / rka 三平台

> 版本：v1.1.52 起（2026-10-19 官方规范对齐重构后）
> 平台名以 `rk / cvis / rka` 为准；**`cvia` 是 `rka` 的历史别名**（早期发布过的平台名，
> 客户端、构建脚本、服务端 `/app-update` 均保留 `cvia -> rka` 归一化）。
> 平台差异的根源只有一个：**A 系列是 uClibc（编原生模块要用 uClibc sysroot）；Eric 库只有 aarch64（只有 rk 能用）**。

## 一、一句话版本

| 平台 | 下载 | 安装 | 重启 | 用户点一次「立即更新」能全自动吗 |
|---|---|---|---|---|
| **rk** | Eric.Shell → `curl` | Eric.Shell → `miniapp_cli install` | Eric.Shell → `miniapp_cli start` | ✅ 全自动（真机验证） |
| **cvis** | updater 原生模块 → `curl` | updater → `miniapp_cli install` | updater → `miniapp_cli start` | ✅ 全自动（代码就绪，**无真机**） |
| **rka**（旧名 cvia） | updater 原生模块 → `curl` | updater → `miniapp_cli install` | updater → `miniapp_cli start` | ✅ 全自动（v1.1.51 起，**无真机**） |

## 二、能力矩阵（决定走哪条分支的就是这张表）

| 能力 | rk | cvis | rka |
|---|---|---|---|
| `libjsapi_Eric.so`（Shell，aarch64） | ✅ 有 | ❌ 无（架构不对） | ❌ 无（架构不对） |
| `libjsapi_updater.so`（自研原生模块） | ✅ aarch64/glibc | ✅ armv7/glibc | ✅ armv7/**uClibc** |
| `jsapi.http.downloadFile`（平台接口） | ⚠️ 存在但会挂住 | ⚠️ 同左 | ⚠️ 同左 |
| **`installCapable()`** | `true` | `true` | `true`（v1.1.51 起） |
| **`downloadCapable()`** | `true` | `true` | `true` |

> 三份原生库的 `DT_NEEDED` 分别是 `libc.so.6` / `libc.so.6` / **`libc.so.0`**，和设备上的完全一致。

> ⚠️ **顺序很重要**：`downloadCapable()` 在三个平台上都是 `true`（平台接口存在但会挂住）。
> 所以判断必须**先 `installCapable()` 再 `downloadCapable()`** —— 这是 v1.1.50 修的 30 秒白等 bug。

## 三、完整链路

```
┌─ 服务端（独立私有项目 delta-mojin-server）────────────────────┐
│  GET /app-update?version=<当前>&platform=<rk|cvis|rka>        │
│    ├ 按 platform 筛 active 记录（platform 空 = 全平台）        │
│    ├ cvia 自动归一化为 rka（历史别名兼容）                     │
│    ├ 版本号按【数字】比较，不是字符串（1.1.9 < 1.1.10）         │
│    └ 返回 {hasUpdate, force, latest:{version,url,size,md5}}    │
│                                                               │
│  GET /pkg/<文件名>.amr        更新包下载（复用同一端口）       │
└───────────────────────────────────────────────────────────────┘
                           ↓
┌─ 客户端 ──────────────────────────────────────────────────────┐
│ ① 触发：首页渲染 → checkServer()                               │
│    （挂在成功回调里 —— 唯一经真机验证会执行的路径；              │
│      onShow / setTimeout 在本框架不可靠）                       │
│ ② 有更新 → 弹窗（force=1 时关不掉）                             │
│ ③ 点「立即更新」→ goStore()                                     │
│    【顺序】先 installCapable()，再 downloadCapable()            │
│      不能装 → 关弹窗 + 提示「请到应用商店更新」                  │
│      能装   → 进入下载                                          │
│ ④ 下载 → downloadPackage(url, version, size)                    │
│    目录 = res/version.js 的 updateDir（/userdisk/DeltaMojinUpdate）│
│    文件名 = update-<版本>.amr                                   │
│ ⑤ 安装 → installAndRestart(path, appid)                        │
│ ⑥ 重启 → 应用自重启，新版本生效                                 │
└───────────────────────────────────────────────────────────────┘
```

平台参数 `platform` 由 **`ui/src/services/platform.js` 的 `updatePlatform()`** 产生：

| 构建产物 | `res/version.js` 的 platform | `updatePlatform()` 行为 |
|---|---|---|
| rk 单包 | `rk` | 直接返回 `rk` |
| cvis 单包 | `cvis` | 直接返回 `cvis` |
| rka 单包 | `rka` | 直接返回 `rka` |
| 家族组合包（cvis / rka） | 对应家族（`cvis`/`rka`，JS 为该家族单包） | 直接返回家族 |
| 跨家族实验包（`--merge-cross`，不发布） | `merged` | 用设备代号 `$falcon.env.custom.theme` 映射家族：rk 代号→`rk`、cvis 代号→`cvis`、A 系列→`rka`；未知代号保守回退 `rk` 并写日志 |

设备代号映射表维护在 `platform.js` 的 `FAMILY_CODES`（rk 12 个代号 / cvis 4 个 / rka 2 个），
新增机型只需加表项。

## 四、每个平台具体走哪段代码

### rk（X3s / X6plus / P5 / X7 / X7 Pro 等）

包里带（`native/libs/arm64-y02-1/`，构建时平铺进 `ui/libs/`）：

```
libs/libjsapi_Eric.so       596,608 B  aarch64 glibc（Shell，自动更新用）
libs/libjsapi_updater.so     39,232 B  aarch64 glibc（自研原生模块）
libs/libjsapi_panet.so      459,616 B  aarch64 glibc（文件/网络 JSAPI，系统库副本）
libs/libjsapi_twofinger.so   68,176 B  aarch64（evdev 双指）
```

`native-mods.js`（构建生成，rk 目标）：

```js
import EricModule from 'Eric'
import updaterModule from 'updater'
export const NATIVE_TARGET = 'rk'
export const MERGE_MODE = false

export const ericShell = (EricModule && EricModule.Shell) || null
export const updater = updaterModule || null

export function getEricShell() { return ericShell }
```

`installRoute()` 命中第一分支 → **shell 路线**（`Eric.Shell`）：

```bash
/usr/bin/miniapp_cli install <updateDir>/update-X.Y.Z.amr
```

### cvis（S7pro / S6pro / X5 系列）

包里带（`native/libs/arm-coco/`）：

```
libs/libjsapi_bridge.so   5,856,772 B  armv7 glibc（组合包中 strip 后 281,948 B）
libs/libjsapi_updater.so     35,480 B  armv7 glibc
```

`native-mods.js`（cvis 目标）：

```js
import updaterModule from 'updater'
export const NATIVE_TARGET = 'cvis'
export const MERGE_MODE = false
export const panet = null
export const ericShell = null
export const updater = updaterModule || null
export function getPanet() { return null }
export function getEricShell() { return null }
```

`installRoute()` 命中第二分支 → **原生模块路线**（`updater`）。模块内部（C++，不经 shell，
参数逐个校验后 `fork` + `execv`）：

```c
download(url, path)  → mkdir -p 逐级建目录 → execv("/usr/bin/curl", [-L,-f,-s,-o,path,url])
install(amrPath)     → execv("/usr/bin/miniapp_cli", ["install", path])
start(appid)         → execv("/usr/bin/miniapp_cli", ["start", appid])
```

返回值是**同步退出码**（0 成功），不是 Promise —— 所以 `installAndRestart` 走同步分支。

日志期望：

```
[native] 平台=cvis | Eric.Shell=undefined | updater: download=function install=function start=function keys=[default,download,install,start,cliPath]
[install] 命令执行入口: updater 模块 | 平台=cvis eric.exec=undefined mod.install=function
[update] 开始下载 vX.Y.Z -> /userdisk/DeltaMojinUpdate/update-X.Y.Z.amr
```

> **为什么 `Eric.Shell=undefined` 而不是报错**：cvis 目标生成 `native-mods.js` 时
> **根本没写那条 import**。ESM 是静态解析的，包里没有 `libjsapi_Eric.so` 时，
> 只要写了 `import ... from 'Eric'`，整页会白屏（try/catch 拦不住）。

### rka（A 系列 y09/y09p；旧名 cvia，arm32 + uClibc）

包里带（`native/libs/arm-y09/`）：

```
libs/libjsapi_updater.so  35,268 B  armv7 uClibc（DT_NEEDED = libc.so.0）
libs/libjsapi_bridge.so  471,256 B  armv7 uClibc
```

`native-mods.js`（rka 目标）与 cvis 相同（只 import updater，`NATIVE_TARGET='rka'`），
`installRoute()` 走完全一样的原生模块路线。日志里平台名是 `rka`（老客户端/老库里可能显示 `cvia`）。

#### uClibc 那份库是怎么编出来的（关键）

zig 只支持 glibc / musl，**不支持 uClibc**；Bootlin 的 uClibc 工具链是 Linux x86_64 可执行文件，
Windows 上跑不了（也没装 WSL）。但我们只需要它的 **sysroot**，两步就够：

```bash
# 1) 用 zig 的 clang 带 uClibc 头文件编出 .o（头文件取自 sysroot）
zig c++ -target arm-linux-gnueabihf -c -fPIC -O2 \
        -fno-exceptions -fno-rtti -fno-unwind-tables \
        -fvisibility=hidden \
        -I <SDK>/include \
        -isystem <sysroot>/usr/include -isystem <sysroot> \
        -o rka.o jsapi_updater.cpp

# 2) 用 zig 的 lld 直接链 libc.so.0 实体文件
zig ld.lld -shared --allow-shlib-undefined \
        -soname libjsapi_updater.so \
        --version-script native/exports.map \
        -o libjsapi_updater.so rka.o <sysroot>/lib/libc.so.0
```

验证结果：`机器=EM_ARM`、`DT_NEEDED=libc.so.0`、导出只有 `custom_init_jsapis`、无隐患符号。

> 关 `-fno-unwind-tables` 很关键：不关的话 arm32 会引入 `__aeabi_unwind_cpp_pr0` / `_Unwind_*`，
> 这些由 libgcc 提供而宿主不一定导出，会让 dlopen 直接失败（rk 和 cvis 两份也是同样处理）。
> 为什么不能走 `-lc`：`sysroot/usr/lib/libc.so` 是 GNU ld 脚本，里面写死绝对路径 `/lib/libc.so.1`，
> Windows 上解析不了，所以绕过脚本直接把 `sysroot/lib/libc.so.0` 喂给 lld。

工具链位置：`_ref/tc/armv7-eabihf--uclibc--bleeding-edge-2018.11-1`（`native/build.mjs` 找它的 sysroot）。

## 五、cvia 历史别名说明

- `cvia` 是早期版本对 A 系列（A6pro/RV1106 一类设备）使用的平台名，v1.1.52 起正式名改为 **`rka`**。
- 兼容点（都不能删）：
  - 构建：`scripts/profiles.mjs` 的 `normalizeTarget('cvia') -> 'rka'`；`native-mods-content.mjs` 同样别名
  - 客户端：`platform.js` 的 `PLATFORM_ALIAS = { cvia: 'rka' }`；`native-mods.js` 也导出同名别名
  - 服务端：`lb_server.py` 的 `/app-update` 把 `cvia` 归一化为 `rka`
  - 客户端配置/日志里仍可能出现 `cvia`（老包/老配置），解析时按别名处理
- 已发布的 rka/老 cvia 包不需要因为改名而重发；只是**新包一律用 rka 名**。

## 六、三条硬约束（都是真机踩出来的）

### ① `curl -o` 不会建目录

第一版没 `mkdir -p`，`curl` 直接失败，但退出码处理有漏洞时表现为「假成功」。
现在 rk 用 `mkdir -p` 命令，cvis/rka 在原生层里逐级 `mkdir()`。

### ② 必须等下载真的完成

Eric 的 `exec` 是异步的。不等 Promise 就进下一步，会变成「下载还没完就开始安装」。

### ③ 绝不能静态 import 一个包里没有的模块

ESM 的 import 在模块求值前就要解析完。包里没有对应 `.so` 时整条 import 链抛错，
**页面根本渲染不出来，而且 try/catch 拦不住**。
所以 `native-mods.js` 是**按目标生成**的（`scripts/native-mods-content.mjs`，
由 `ui/scripts/test-native-mods.mjs` 锁定四目标输出：rk/cvis/rka/merged）。

## 七、失败与降级矩阵

| 情况 | 表现 |
|---|---|
| 服务端 unreachable | 底部状态点变红「服务器连接失败」，不弹更新窗 |
| 没有更新 | 点「检查更新」→ 底部闪黄字「已是最新版本 vX」，3 秒恢复排版，**不弹窗** |
| 有更新、能装 | 弹窗 → 下载 → 安装 → 重启（全自动） |
| 有更新、装不了 | 弹窗 → 点更新 → 关弹窗 + 提示去商店（**不下载**） |
| 下载失败 | 弹窗内显示「下载失败: curl-<退出码>」 |
| 安装失败 | 「安装失败(install) code=<码>」 |
| 服务端发了 `force=1` | 弹窗关不掉，只能点「立即更新」 |
| 跨家族实验包在 rk 上 | 能启动，但 `tryRequire('panet')` 拿不到模块 → 文件读取/双指/安装降级（**故不作正式产物**） |
