# 屏幕适配机制（全设备）

> 2026-10-19 新增。背景：用户反馈 **X6P（YDPX6，client 代号 melon）UI 显示不全**。
> 本文记录适配链路、各页面公式、设备矩阵、诊断方法和真机验证步骤。
> 结论：**不再假设逻辑高度固定 266px**，一切按 `$falcon.env.deviceWidth/deviceHeight` 实时换算。

---

## 一、官方依据

- `$falcon.env.deviceWidth / deviceHeight` = **设备物理分辨率-宽/高**（官方 `04-posc-docs/jsapi/env/global.md:15-16`）。
- `app.js` 的 `setViewPort(960)`：把 960 逻辑宽映射到设备物理宽，即 **1 逻辑 px = 物理宽 / 960**。
- 因此页面逻辑高度 = `round(960 × 物理短边 / 物理长边)`（横竖屏通用）。
- 参考机型：y02-1（X7 Pro）物理 936×280 → 逻辑 960×287；官方设计基准 960×266。

## 二、计算链路与布局单位（vh / vw）

**布局策略（2026-10-19 X6P 实测后定稿）**：根容器/遮罩用 100vw / 100vh 铺满；元素尺寸统一用 vw（逻辑宽固定 960，1px=0.10417vw，即设计尺寸，不随设备高度拉伸）；滚动区/列表高度仍按 pageH 自适应，兼容 3.6:1～5:3 各种屏幕。旧固件不支持 vw/vh 时用前置的 px/% 降级声明兜底（X3S 黑屏修复）。

> 曾尝试把全部纵向尺寸改成 vh 做等比缩放：X6P（800×480 → 逻辑 960×576）上元素被放大 2.16 倍，反而严重溢出，已回退。（`04-posc-docs/app/css/common/common.md` 明确支持
`px rpx % vw vh`），不再用 JS 按 `pageH - 常量` 算 px：

```
设计基准 960×266（y02-1 逻辑视口 960×287）
  横向: 1 设计 px = 0.10417vw   (100vw = 960 逻辑宽)
  纵向: 1 设计 px = 0.37594vh   (100vh = 设备逻辑高，随视口高缩放)
  · 页面根/背景/内容容器: width 100vw; height 100vh
  · 遮罩/覆盖层: height 100vh（一定能盖满）
  · 面板/滚动区/卡片/菜单/按钮/图标: 高度用 vh，宽度用 vw；
    圆形/方形控件（宽高相同）两个方向都用 vh，保证不被拉成椭圆
  · 字号/行高/纵向 margin、padding: vh；横向 margin、padding: vw
  · 游戏页 DOM 控件同样 vh；canvas 用 100vh，引擎内部视口仍按 canvas 实际像素动态计算
```

`screen.js` 仍负责取真实逻辑高（诊断/日志/游戏引擎/触摸命中用），页面布局本身不再依赖 pageH：

```
app.onLaunch: setViewPort(960)                        app.js
  └─ screen.js: screenInfo()
       env($falcon.env.deviceWidth/Height, 100..5000)
         → window.innerWidth/Height（Falcon 页面通常没有 window）
         → document.documentElement
         → 960×266 兜底
     logicalHeight = round(960 × min / max)，下限 120（不再钳到 266）
     pageSize() = { w: 960, h: logicalHeight }   ← 只用于诊断/引擎/触摸
  ├─ 页面布局: 纯 CSS vh/vw（不写死 266，短屏/高屏按比例伸缩）
  ├─ game.vue: pageH → engine.setViewport；触摸矩形按 k=pageH/266 换算
  └─ 日志: [ui]/[game-screen] 输出 pageH 与关键尺寸，便于远程定位
```

> 为什么还需要 pageH：canvas 像素、引擎逻辑视口、触摸命中矩形、诊断日志必须是数值；
> 布局本身已全部交给 vh/vw，两者职责分离。

## 三、游戏页（引擎）适配

旧实现 `VIEW_W=960 / VIEW_H=266` 固定，渲染时底部对齐：
- 高屏（如 287/320）→ 顶部留黑条、HUD 下移；
- 矮屏（<266）→ 顶部被裁（HUD/撤离进度不可见），DOM 控件与画面错位。

新实现：
- `Game.prototype.setViewport(w,h)`：`game.vue` 启动/切后台回来时注入真实 `pageH`；
- `Game.prototype._syncViewport(cw,ch)`：每帧按 canvas 实际像素反算逻辑视口 `viewH = ch / (cw/viewW)`，`offY = 0`，画面 1:1 铺满；
- HUD/相机/剔除/暂停遮罩全部改用 `this.viewW/this.viewH`；
- DOM 触摸热区（`_touchLayout`）与 canvas 使用同一 `pageH`，native `createTwoFinger({width:960,height:pageH,rotation:90})` 同源。

## 六、X6P 实测数据（2026-10-19 用户日志）

- 设备：X6P，theme-melon，client=melon → 归 rk 家族；platform=rk 单包
- 物理分辨率 800×480（5:3），fw 1.4.0，env 可用
- 逻辑视口 = 960 × 576（960×480/800）
- 旧版实测：[game-screen] engineView=960x=266.00（引擎仍按 266 画，画布/触控比例错误）
- 触控：screenX/screenY 为物理像素；控件矩形为逻辑坐标 → 需按 960/800、576/480 换算，即触控偏移根因
- 修复后日志新增：[game-screen] actualCanvas=…、[touch-map] raw=… -> logical=…、[touch] first …

## 七、已知风险 / 待确认

- `env` 语义是否在所有固件上都是物理像素（若为逻辑值，canvas 会纵向拉伸）——需 X6P 真机比对。
- 深层节点 `height:100%` 在部分节点不可靠，所以弹窗/滚动区一律显式 px（本页公式）。
- DOM 触摸降级路径优先 `screenX/screenY`；若其单位为物理像素，摇杆可能有最多 ≈24px 偏移（native 路径不受影响）——需真机确认。
- `vh/vw` 官方支持但未采用（行为需真机验证），当前统一用 `pageH` 计算。
